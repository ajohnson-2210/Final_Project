# Cambridge-Style Pseudocode — AJ_24038155 Dialect v1.3

## Status

This document defines the **v1.3 delta** from the frozen AJ_24038155 Dialect v1.2 specification. All v1.0, v1.1 and v1.2 lexical, syntactic and semantic rules remain normative unless explicitly changed below.

v1.3 adds two explicit language capabilities required by the study corpus:

1. runtime conversion between primitive values using explicit `CALL` casts; and
2. explicit whole-program termination using `QUIT`.

The additions are deliberately narrow. They do not introduce implicit type coercion, runtime type introspection, substring slicing, callbacks, or first-class functions.

## 1. Explicit runtime casts

### 1.1 Canonical syntax

Runtime conversion uses `CALL` followed by a primitive cast target:

```text
CALL INTEGER(expression)
CALL FLOAT(expression)
CALL STRING(expression)
```

The preceding `CALL` is semantically significant and distinguishes a runtime cast from the existing typed-literal constructors.

```text
INTEGER(23)               COMMENT typed integer literal
CALL INTEGER(value)       COMMENT runtime conversion

FLOAT(3.5)                COMMENT typed float literal
CALL FLOAT(value)         COMMENT runtime conversion

STRING("23")              COMMENT string literal
CALL STRING(value)        COMMENT runtime conversion
```

### 1.2 Grammar extension

```text
cast_expression ::=
    "CALL" , cast_type , "(" , expression , ")" ;

cast_type ::=
    "INTEGER"
  | "FLOAT"
  | "STRING" ;
```

`cast_expression` is added to `primary_expression`.

Each cast accepts exactly one argument.

### 1.3 Semantics

`CALL INTEGER(expression)` converts the evaluated value to an integer using deterministic Python-compatible runtime conversion semantics. Invalid conversions raise a runtime error and may therefore be handled by an enclosing AJ `TRY ... CATCH`.

`CALL FLOAT(expression)` converts the evaluated value to a floating-point value using deterministic Python-compatible runtime conversion semantics. Invalid conversions raise a runtime error.

`CALL STRING(expression)` converts the evaluated value to its textual representation using deterministic Python-compatible runtime conversion semantics.

The compiler must not insert any of these conversions implicitly. A cast occurs only where the AJ source explicitly contains the corresponding `CALL` expression.

### 1.4 Python translation

```text
CALL INTEGER(value)  -> int(value)
CALL FLOAT(value)    -> float(value)
CALL STRING(value)   -> str(value)
```

Example:

```text
TRY
    givenNum <- CALL INTEGER(givenNum)
CATCH
    OUTPUT STRING("Invalid integer")
ENDTRY
```

translates deterministically to the corresponding Python `int(...)` conversion within a `try`/`except` region.

### 1.5 AST representation

A cast is represented explicitly as a `CastNode` containing:

- `target_type`; and
- the source expression being converted.

This preserves conversion intent for AST, flow-diagram and scoring/audit stages instead of disguising the cast as an ordinary user-defined function call.

## 2. Program termination with QUIT

### 2.1 Canonical syntax

```text
QUIT
```

`QUIT` is a statement and may appear at top level or inside a block.

### 2.2 Semantics

`QUIT` terminates execution of the current program immediately. It is distinct from:

- `RETURN`, which exits the current function and remains invalid at top level;
- `BREAK`, which exits the nearest loop only; and
- `CONTINUE`, which begins the next iteration of the nearest loop.

Therefore a source-level Python `quit()` used to terminate the complete algorithm is represented canonically by `QUIT`, not by a top-level `RETURN` or `BREAK`.

### 2.3 Grammar extension

```text
quit_statement ::= "QUIT" , newline ;
```

`quit_statement` is added to `statement`.

### 2.4 Python translation

```text
QUIT -> quit()
```

### 2.5 Control-flow semantics

A `QUIT` node is terminal. The flow diagram must not connect it to a following executable statement or route it back to a loop decision. Its path terminates at an END node.

The AST uses a dedicated `QuitNode` so the source's explicit termination intent remains distinguishable from legacy `STOP` compatibility syntax.

## 3. Reserved identifier interaction

`INTEGER`, `FLOAT`, `STRING` and `QUIT` are reserved AJ keywords. The existing source-proven restricted-identifier escape rule remains applicable when source syntax unambiguously proves that one of these spellings is instead being used as an identifier binding.

For example:

```text
quit <- BOOLEAN(FALSE)
```

may be normalised to a protected internal identifier under the established `__reserved_keyword__...` convention, while a standalone canonical:

```text
QUIT
```

retains its program-termination meaning.

## 4. Backwards compatibility

All canonical AJ v1.2 programs remain valid under v1.3.

The pipeline's historical `STOP` compatibility statement remains accepted for existing corpus material, but new canonical v1.3 pseudocode should use `QUIT` when the intended semantics are whole-program termination corresponding to Python `quit()`.

Typed literal constructors remain unchanged. In particular, `INTEGER(variable)` is not reinterpreted as a runtime cast; runtime conversion requires the explicit `CALL INTEGER(variable)` form.

## 5. Versioning

This language revision is recorded as:

**AJ_24038155 Dialect v1.3**

Any later syntax addition, removal or semantic alteration must create a new dialect version.

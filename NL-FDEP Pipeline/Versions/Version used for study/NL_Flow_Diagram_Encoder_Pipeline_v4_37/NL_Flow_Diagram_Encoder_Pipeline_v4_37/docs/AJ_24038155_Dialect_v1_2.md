# Cambridge-Style Pseudocode — AJ_24038155 Dialect v1.2

## Status

This document defines the **v1.2 delta** from the frozen AJ_24038155 Dialect v1.1 specification. All v1.0 and v1.1 lexical, syntactic and semantic rules remain normative unless explicitly changed below.

Version v1.2 is introduced because nested/local function declarations are now part of the canonical dialect. This permits source scope to be preserved when an algorithm declares a helper function inside another function rather than forcing the helper to be hoisted to module scope.

v1.2 does **not** add callbacks, first-class function values, anonymous functions, or a function-reference expression. Those features are reserved for a later dialect revision.

## 1. Nested/local function declarations

### 1.1 Canonical syntax

A `FUNCTION ... ENDFUNCTION` declaration may appear inside the body of another function:

```text
FUNCTION outer ACCEPTS(value)
    FUNCTION inner ACCEPTS(item)
        RETURN item
    ENDFUNCTION

    RETURN CALL inner(value)
ENDFUNCTION
```

A function declared inside another function is a **nested function** (also called a **local function**).

The declaration uses the existing canonical function syntax. No new callback or function-reference syntax is introduced.

### 1.2 Grammar extension

The existing function declaration remains:

```text
function_declaration ::=
    "FUNCTION" , identifier , "ACCEPTS" ,
    "(" , [ parameter_list ] , ")" , newline ,
    function_body ,
    "ENDFUNCTION" , newline ;
```

In v1.2, `function_declaration` is also permitted as a statement while parsing an executable block inside a function body:

```text
function_body ::= { function_body_item } ;

function_body_item ::=
    statement
  | function_declaration
  | comment ;
```

Because a nested function has an ordinary function body, nesting may be recursive: a nested function may itself declare another nested function.

### 1.3 Scope and name visibility

A nested function name belongs to the lexical scope in which the declaration appears. It is not promoted to top-level/module scope.

The nested function may call itself recursively by name.

A nested function may read values that are already visible in an enclosing lexical scope. An assignment to a simple identifier inside the nested function creates or updates that nested function's own local binding under the existing assignment rules; v1.2 introduces no `nonlocal`-style rebinding construct.

Code outside the enclosing function must not rely on the nested function name being visible.

### 1.4 Calls

Nested functions are invoked with the existing call syntax:

```text
CALL inner(argument)
```

No special callback invocation syntax is added.

### 1.5 Python translation

A nested AJ function translates to a nested Python `def` at the corresponding lexical indentation.

AJ v1.2:

```text
FUNCTION outer ACCEPTS(N)
    FUNCTION helper ACCEPTS(value)
        OUTPUT value
    ENDFUNCTION

    CALL helper(N)
ENDFUNCTION
```

Python:

```python
def outer(N):
    def helper(value):
        print(value)

    helper(N)
```

The compiler must not hoist `helper` to module scope merely to simplify code generation.

## 2. Callback and first-class function boundary

v1.2 adds **declaration nesting only**. It does not make function declarations into general expression values.

The following capabilities are **not introduced by v1.2**:

```text
callback <- FUNCTION_REFERENCE(transform)
CALL apply(value, transform)
RETURN transform
APPEND transform TO handlers
```

where `transform` denotes a function declaration rather than an ordinary data value.

A later dialect revision may define function references, callback parameters, callable-value typing, storage of function values, and any required closure/escape semantics. v1.2 deliberately leaves those questions unchanged and out of scope.

## 3. Backwards compatibility

All canonical AJ v1.1 programs remain valid under v1.2.

Top-level `FUNCTION` declarations retain their existing meaning. Class `METHOD` and `CONSTRUCTOR` syntax is unchanged. The v1.2 change only makes lexical nesting of ordinary `FUNCTION` declarations canonical where the source contains that structure.

Compatibility normalisation should preserve a supplied nested-function relationship when it can be recovered from the source. It must not hoist a nested helper or manufacture a nested helper that the source did not contain.

## 4. Tower of Hanoi example

The following structure is canonical AJ v1.2:

```text
FUNCTION unnamed_function ACCEPTS(N)
    FUNCTION Hanoi ACCEPTS(Discs, Source, Auxiliary, Destination)
        IF Discs == 1 THEN
            OUTPUT STRING("Move disk from {Source} to {Destination}")
        ELSE
            CALL Hanoi(Discs - 1, Source, Destination, Auxiliary)
            OUTPUT STRING("Move disk from {Source} to {Destination}")
            CALL Hanoi(Discs - 1, Auxiliary, Source, Destination)
        ENDIF
    ENDFUNCTION

    CALL Hanoi(N, STRING("A"), STRING("B"), STRING("C"))
ENDFUNCTION
```

Its deterministic Python structure is:

```python
def unnamed_function(N):
    def Hanoi(Discs, Source, Auxiliary, Destination):
        if Discs == 1:
            print(f"Move disk from {Source} to {Destination}")
        else:
            Hanoi(Discs - 1, Source, Destination, Auxiliary)
            print(f"Move disk from {Source} to {Destination}")
            Hanoi(Discs - 1, Auxiliary, Source, Destination)

    Hanoi(N, "A", "B", "C")
```

`N` remains an externally supplied value. The nested function is not hoisted, and no interactive input prompt is implied by this structure.
